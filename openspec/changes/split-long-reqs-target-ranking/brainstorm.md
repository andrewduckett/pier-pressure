| # | Question | Answer | Source |

| D1 | Which requirements does this story split? | The 5 that `openspec validate --specs` flags in `target-ranking`: "Targets are gated before ranking", "Each target carries its computed observing geometry", "Targets are scored and ordered deterministically", "Each target carries its size and brightness" and "The verdict says how the top pick frames". "Catalog is loaded from a pinned offline source" and "Catalog is filtered to observable objects" are under the limit and stay as they are. | Evidence: #235 body; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `target-ranking`? | No. No open pull request edits `openspec/specs/target-ranking/`, and no remote branch holds a change to it. | Evidence: `gh pr list`; `gh pr diff <n> --name-only` for each open pull request |
| D3 | How many scenarios may this story add? | Only where a split-out behavior would otherwise have no scenario, since strict validation rejects an ADDED requirement without one. Each added scenario restates a SHALL its requirement keeps, and an existing test already asserts it. The pull request lists each one. | Assumption (the user delegated the brainstorm). Evidence: #234 brainstorm D3; #230 Shared decision 4 |
| D4 | How does "Targets are gated before ranking" split? | Into three: a candidate must clear the mask for the minimum duration; every listed target's window spans that duration; a night with no dark window has no targets. Each keeps the scenarios that test it. No scenario is added. | Evidence: `openspec/specs/target-ranking/spec.md`, one or two scenarios per behavior |
| D5 | How does "Each target carries its computed observing geometry" split? | Into four: the geometry each target carries; the window clamp to the dark window; the transit time as that day's meridian crossing; whole-second UTC times. The last two each get one added scenario, backed by `tests/test_ranking_geometry.py` `test_circumpolar_daytime_transit_is_outside_the_window` and `tests/test_ranking_pipeline.py` `test_every_emitted_target_is_whole_second_and_scored`. | Assumption. Evidence: `openspec/specs/target-ranking/spec.md`; those tests |
| D6 | How does "Targets are scored and ordered deterministically" split? | Into nine: the six factors; the moon factor's neutral case; how brightness is judged; how field-of-view fit is judged; the progressive oversize penalty; when a factor contributes; renormalising the weights; the top 10 in a stable order; determinism. The moon factor gets one added scenario, backed by `tests/test_ranking_score.py` `test_moon_subscore_neutral_when_moon_down`. The other ten scenarios move over whole. | Assumption. Evidence: `openspec/specs/target-ranking/spec.md`; `pierpressure/core/ranking.py` |
| D7 | How does "Each target carries its size and brightness" split? | Into two: each target carries its catalog size and brightness, null when unrecorded; the ranking's brightness choice changes no carried value. The second gets one added scenario, backed by `tests/test_ranking_pipeline.py` `test_targets_carry_the_raw_catalog_facts`. | Assumption. Evidence: `openspec/specs/target-ranking/spec.md`; that test |
| D8 | How does "The verdict says how the top pick frames" split? | Into five: when the verdict gets one framing sentence, how it names the pick and where it goes in `reasons[]`; then one requirement per framing sentence, each stating the condition that picks it. Each sentence requirement keeps the scenario for its sentence. No scenario is added. | Assumption. Evidence: `openspec/specs/target-ranking/spec.md`; `pierpressure/core/ranking.py` `equipment_reasons` |
| D9 | The code disagrees with "The verdict says how the top pick frames" in two ways. Does this story fix that? | No. The code also adds "Top pick `<name>` is a bright target." for a bright pick, which no spec names. It also withholds the top-pick sentences when the scored window is under an hour, a condition the requirement does not list. The epic changes no behavior or meaning (Shared decision 3), so the new requirements keep the old meaning. The REMOVED **Reason** and the pull request report the drift. | User (the issue brief says to keep the meaning and report the drift). Evidence: `pierpressure/core/ranking.py` lines 319–349; `pierpressure/core/producer.py` lines 51–65; `tests/test_producer_targets.py` `test_a_window_not_worth_setting_up_for_carries_no_equipment_reason` |
| D10 | May the SHALL text be reworded? | Only so that each new requirement reads on its own, such as naming its subject again or stating the precedence a numbered list gave. Every SHALL, SHALL NOT and MAY keeps its meaning. | Evidence: #230 Shared decision 3 |
| D11 | Which words do the new headings use? | The words the spec already uses: target, candidate, target list, horizon mask, minimum duration, dark window, observing geometry, transit time, factor, field-of-view fit, top pick and framing sentence. The glossary defines none of them, and no term is new. No heading repeats a heading the delta removes or one the spec keeps. | Evidence: `openspec/glossary.md`; `openspec/specs/target-ranking/spec.md` headings; #230 Shared decision 5 |
| D12 | What does "done" mean for this story? | `openspec validate split-long-reqs-target-ranking --strict` passes before archive; after archive `target-ranking` has no long-requirement warning; the epic's check with `TARGET=split-long-reqs-horizon-mask` and `CAPS=target-ranking` prints `OK: target-ranking` with 4 scenarios added; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #250 |

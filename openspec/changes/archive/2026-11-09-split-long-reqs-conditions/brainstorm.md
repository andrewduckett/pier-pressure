## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which requirements does this story split? | The 9 that `openspec validate --specs` flags in `conditions`, as the issue lists them. The other 44 requirements are under the limit and stay as they are. | Evidence: #236 body; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `conditions`? | No. Open pull requests #246 and #255 edit only `openspec/discovery.md`, the stack's own pull requests edit other specs, and no remote branch holds a change to `openspec/specs/conditions/`. | Evidence: `gh pr list`; `gh pr diff <n> --name-only`; `git diff origin/main...<branch>` for the other remote branches |
| D3 | How many scenarios may this story add? | Only where a split-out behavior would otherwise have no scenario, since strict validation rejects an ADDED requirement without one. Each added scenario restates a SHALL its requirement keeps, and an existing test already asserts it. The pull request lists each one. | Assumption (the user delegated the brainstorm). Evidence: #235 brainstorm D3; #230 Shared decision 4 |
| D4 | How does "Cloud cover carries a low/mid/high component split" split? | Into three: the cloud data carries the three layers with the total, as one bundle; each layer is marked available on its own; the split leaves the total's meaning unchanged, and a total-only provider still yields a valid snapshot. Each keeps one of the 3 scenarios. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md` |
| D5 | How does "Each fetch reports its outcome per provider" split? | Into eight: one outcome per provider in order, naming it and its variables; a success carries the issue time; a failure carries a short error; no readings means failed; readings mean successful; the error is built only from safe parts; the error copies no text from the error or response; outcomes never reach the verdict. All 11 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; `pierpressure/health.py` `describe_error` |
| D6 | How does "A failed computed outcome says which input was missing" split? | Into four: an error part for each variable that computed nothing, how parts are joined, and when there is none; then one requirement per fixed reason (missing input, no shared hour, the kind of a raised error). All 6 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; `pierpressure/conditions/provider.py` `ComputedSource.derive` |
| D7 | How does "Each variable is filled from the first provider in order that returned it" split? | Into two: the first provider in order that returned a variable fills its one series, and a variable nobody filled has none; a provider fills a bundle whole or not at all. Its 6 scenarios divide 3 and 3. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md` |
| D8 | How does "The computed source reports an outcome like a provider" split? | Into four: one outcome at its place in the order; success when a computed hour has a value; the oldest computed issue time; the providers each variable read. All 6 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; `pierpressure/conditions/provider.py` |
| D9 | How does "The snapshot keeps alternates beside the filled series" split? | Into three: each later provider that returned a variable leaves an alternate, carrying what a filled series carries; a provider that returned nothing or failed leaves none; alternates never change the filled series. All 7 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md` |
| D10 | How does "NWS periods are expanded onto the hourly grid within a 72-hour horizon" split? | Into three: each value is held across its period's hours, and an uncovered hour stays absent; precipitation probability is held one hour later; only hours within the 72-hour horizon are kept. All 8 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; `pierpressure/conditions/nws.py` |
| D11 | How does "Each Open-Meteo model declares the variables its model returns" split? | Into four: HRRR and GFS declare what `open_meteo` does; ICON drops column water vapour and the seeing column; HRDPS and RDPS also drop precipitation probability; a provider without the seeing column declares none of its variables. All 8 scenarios move over whole. No scenario is added. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; `pierpressure/core/providers.py` |
| D12 | How does "Every Open-Meteo request asks for the 4 hours before the fetch and the 72 after" split? | Into two: every hourly request asks for 4 past and 72 forecast hours, from every Open-Meteo provider; no hourly request asks for forecast days, and each asks for UTC. The second gets one added scenario, backed by `tests/test_conditions_provider.py` `test_every_open_meteo_request_asks_for_4_past_hours_and_72_ahead`. | Assumption. Evidence: `openspec/specs/conditions/spec.md`; that test |
| D13 | Does the code disagree with any of the 9 requirements? | No drift found. Each requirement's SHALLs were checked against `pierpressure/health.py`, `pierpressure/conditions/provider.py`, `pierpressure/conditions/nws.py`, `pierpressure/conditions/open_meteo.py` and `pierpressure/core/providers.py`. | Evidence: those files |
| D14 | May the SHALL text be reworded? | Only so that each new requirement reads on its own, such as naming its subject again, or naming the inputs where the original said "listed above". Every SHALL and SHALL NOT keeps its meaning. | Evidence: #230 Shared decision 3 |
| D15 | Which words do the new headings use? | The glossary's terms (provider, series, bundle, provider order, alternate, computed source) and the spec's own words (outcome, snapshot, issue time, seeing column, model provider). No term is new. No heading repeats a heading the delta removes or one the spec keeps. | Evidence: `openspec/glossary.md`; `openspec/specs/conditions/spec.md` headings; #230 Shared decision 5 |
| D16 | What does "done" mean for this story? | `openspec validate split-long-reqs-conditions --strict` passes before archive; after archive `conditions` has no long-requirement warning; the epic's check with `TARGET=split-long-reqs-target-ranking` and `CAPS=conditions` prints `OK: conditions` with 1 scenario added; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #256 |

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which requirements does this story split? | The 8 `ha-delivery` requirements the issue names: "Provider health is exposed as diagnostic entities" (14 scenarios), "Narrative is exposed as an optional entity" (5), "Each rank of the target list is exposed as an entity" (6), "Top target is exposed as an entity" (3), "Verdict state and attributes are exposed" (4), "The Cloud cover state is the current hour's value" (3), "Per-pier entity auto-discovery" (2) and "Each further timeline variable is exposed as an entity" (4). They are the only 8 long-requirement warnings left in `ha-delivery`, so this story leaves none. | Evidence: #241 body; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `ha-delivery`? | No. Open pull requests #246 and #255 edit only `openspec/discovery.md`, and the stack's other open layers do not edit the 8 requirements. | Evidence: `gh pr list`; `gh pr diff <n> --name-only` |
| D3 | How does "Per-pier entity auto-discovery" split? | Into two: discovery for the verdict, score and refresh entities; their identity from the pier, so a republish updates them. | Assumption (the user delegated the brainstorm). Evidence: `openspec/specs/ha-delivery/spec.md` |
| D4 | How does "Verdict state and attributes are exposed" split? | Into three: the verdict state and the details in its attributes; the attributes leave out only the timeline; the score state, unavailable when the score is null. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D5 | How does "Top target is exposed as an entity" split? | Into four: discovery; the state is the top target's name, with the list in its attributes; identity from the pier; unavailable when the list is empty. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D6 | How does "Narrative is exposed as an optional entity" split? | Into seven: nothing published when disabled; no automatic removal of an entity left by an earlier configuration; discovery when enabled; the prose in the attributes, not the state; actively unavailable when a publish has no narrative; a missing or disabled narrative holds back no other entity; identity from the pier. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D7 | How does "Each rank of the target list is exposed as an entity" split? | Into five, along its own paragraphs: a rank sensor for every rank, enabled by default; a filled rank shows its target; an empty rank is unavailable; every publish updates every rank; the retained discovery and identity from the pier and the rank. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D8 | How does "Provider health is exposed as diagnostic entities" split? | Into twelve: one sensor per provider, named after it; its discovery; its state, from memory only; the startup reset; the reset sent again after a drop; three attribute groups (provider, variables and tracking start; the latest fetch; the issue time of the last success); the computed source's `inputs`; a failed fetch keeps the last success; available while online; health beside the verdict document. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D9 | How does "The Cloud cover state is the current hour's value" split? | Into two, the way the spec already splits the further timeline sensors: the state is the current hour's value; with no such value it shows unknown and stays available. | Assumption. Evidence: "A further timeline sensor's state is its variable's current-hour value" and "A further timeline sensor with no current-hour value shows unknown and stays available" in `openspec/specs/ha-delivery/spec.md` |
| D10 | How does "Each further timeline variable is exposed as an entity" split? | Into two: a sensor for each of the sixteen keys; its retained discovery and identity from the pier and the key. | Assumption. Evidence: `openspec/specs/ha-delivery/spec.md` |
| D11 | How many scenarios does this story add? | Four, one for each new requirement that none of the original scenarios fits: "An unnamed top target shows its designation", "A narrative entity from an earlier configuration is left in place", "The narrative state does not carry the prose" and "Each health sensor is named after its provider". Each restates a rule its requirement keeps, and an existing test asserts it: `test_state_falls_back_to_id_when_no_common_name` (`tests/test_top_target.py`), `test_disabled_delivery_publishes_no_narrative` and `test_enabled_present_publishes_prose_in_attributes_with_short_state` (`tests/test_narrative_delivery.py`), and `test_health_discovery_validates_and_is_a_diagnostic_timestamp` (`tests/test_health_delivery.py`) with the provider name "7Timer!" in `pierpressure/core/providers.py`. The pull request lists all four. | Assumption. Evidence: those tests; #230 Shared decision 4 |
| D12 | Is any quoted pointer, in any spec, aimed at a heading this story removes? | No. No spec quotes any of the 8 headings. "(spec ha-delivery)" in `verdict-narrative` names the spec, not a heading, and stays. | Evidence: whitespace-normalized search of `openspec/specs` |
| D13 | What about code and tests that name a removed heading? | None does. A search of `pierpressure`, `tests`, `card`, `docs` and `README.md` finds none of the 8 headings. The pull request says so. | Evidence: that search |
| D14 | Does the code disagree with any of the 8 requirements? | No drift found in spot checks: the top-target name falls back to the catalog id, which the catalog calls the designation; the narrative state is the short marker `ready`; health availability is the last-will topic only; the rank, narrative and top-target availability templates; and `docs/llm-explainer.md` documents clearing an orphaned narrative entity. | Evidence: `pierpressure/delivery/mqtt.py`; `pierpressure/core/catalog.py`; `docs/llm-explainer.md` |
| D15 | May the SHALL text be reworded? | Only so that each new requirement reads on its own, such as naming its entity again. The health attributes list opens with one "SHALL carry", and each of its three attribute requirements, plus the computed source's `inputs`, repeats it. So the count goes from 68 SHALL (9 SHALL NOT) to 71 SHALL (9 SHALL NOT), with no MAY before or after. Nothing new is required, and nothing is dropped. | Evidence: #230 Shared decision 3 |
| D16 | Which words do the new headings use? | The spec's own words, and the glossary's provider, computed (source), timeline and variable, with their glossary meaning. No term is new. No ADDED heading repeats a heading the delta removes or one the spec keeps. | Evidence: `openspec/glossary.md`; #230 Shared decision 5 |
| D17 | What does "done" mean for this story? | `openspec validate split-long-reqs-ha-delivery-entities --strict` passes before archive; after archive `ha-delivery` gives no long-requirement warning; the epic's check with `TARGET=split-long-reqs-ha-delivery-broker` and `CAPS=ha-delivery` prints `OK: ha-delivery` with the 4 added scenarios; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #261 |

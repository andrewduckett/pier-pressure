## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which requirements does this story split? | The 7 that `openspec validate --specs` flags in `night-card`: "The docs describe the Cloud range row", "The card draws the four cloud rows", "The strip stays where the user panned it", "The strip spans the judged night", "A Cloud range row with no column says why", "A missing sensor leaves its row empty" and "The card draws every timeline row". The other 116 are under the limit and stay as they are. | Evidence: #233 body; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `night-card`? | No. No open pull request or remote branch changes `openspec/specs/night-card/`. | Evidence: `gh pr list`; `gh pr view 246 --json files`; `git diff origin/split-long-reqs-verdict-narrative...<branch>` for each remote branch |
| D3 | How many scenarios may this story add? | Only where a split-out behavior would otherwise have no scenario, since strict validation rejects an ADDED requirement without one. Each added scenario restates a SHALL the requirement keeps, and an existing test already asserts it. The pull request lists each one. | Assumption (the user delegated the brainstorm). Evidence: #232 brainstorm D6; #230 Shared decision 4 |
| D4 | How does "The card draws the four cloud rows" split? | Into three: the strip sits below the verdict, score and confidence; the cloud rows come under Moon altitude, in their order and with their labels; each of the four cloud rows reads its own sensor. "The rows and their sensors" stays whole under the second. The first and third each get one added scenario, backed by `card/test/strip.test.ts` "are drawn under the verdict lines" and "reads the cloud sensors named from the pier". | Assumption. Evidence: `openspec/specs/night-card/spec.md`; `card/test/strip.test.ts` |
| D5 | How does "The strip spans the judged night" split? | Into three: the strip opens on the opening axis until a pan and after `Back to tonight`; where the opening axis starts and how long it is; the opening axis moves on as the card redraws. Start and length stay together, because every scenario that tests one also tests the other. "Before the first verdict" goes with the first, "A minute passes during the night" with the third, and the other 7 with the second. | Assumption. Evidence: each scenario's THEN in the main spec |
| D6 | How does "The card draws every timeline row" split? | Into two: the strip has sixteen labelled rows, or fifteen without Cloud range; the rows' order from top to bottom. "The rows without Cloud range" goes with the first, "The rows in order" with the second. | Evidence: `openspec/specs/night-card/spec.md`, one scenario per behavior |
| D7 | How does "A missing sensor leaves its row empty" split? | Into two, each naming the rows it covers: a missing, unavailable or forecast-less sensor leaves its row labelled, empty and with its message; a missing sensor or an unreadable point never stops the other rows. "Humidity is unavailable" goes with the first, "Only the sun and cloud sensors" with the second. | Evidence: `openspec/specs/night-card/spec.md`, one scenario per behavior |
| D8 | How does "A Cloud range row with no column says why" split? | Into three: a row with no column shows the first cause that applies; a row with a column shows no message; the card never shows `Needs two forecasts`. The 4 message scenarios go with the first; "One cloud provider" and "Before the first verdict" go with the third. The second gets one added scenario, backed by `card/test/range.test.ts` "shows no message". | Assumption. Evidence: `openspec/specs/night-card/spec.md`; `card/test/range.test.ts` |
| D9 | How does "The docs describe the Cloud range row" split? | Into two: what the docs say the row reads and shows (the first six items); what they say about leaving the row out and `No forecast` (the last two). The existing scenario stays whole under the first, which two of its three checks test. The second gets one added scenario, backed by `tests/test_night_card_doc.py` `test_docs_strip_section_says_when_the_cloud_range_row_is_left_out`. | Assumption. Evidence: `docs/night-card.md`; `tests/test_night_card_doc.py` |
| D10 | How does "The strip stays where the user panned it" split? | Into six, one per SHALL group: a panned strip keeps its start; it moves only as far as the reach needs; a pan the reach stops counts as no pan; a pan back to the opening axis counts as `Back to tonight`; the opening axis catches up with a later pan; an earlier pan keeps its start. "A new night of another length" and "A new pier" go with the first. No scenario is added. | Evidence: each scenario's WHEN and THEN in the main spec |
| D11 | May the SHALL text be reworded? | Only so that each new requirement reads on its own, such as naming its subject or the rows it covers again. Every SHALL keeps its meaning. | Evidence: #230 Shared decision 3 |
| D12 | Which words do the new headings use? | The words the spec already uses: strip, row, Cloud range row, opening axis, reach, pan, `Back to tonight`, Verdict sensor, and "Moon altitude or weather" for the rows D7 covers. No heading repeats a heading the delta removes or one the spec keeps. No term is new. | Evidence: `openspec/glossary.md` (Night strip, Timeline); `openspec/specs/night-card/spec.md` headings; #230 Shared decision 5 |
| D13 | What does "done" mean for this story? | `openspec validate split-long-reqs-night-card --strict` passes before archive; after archive `night-card` has no long-requirement warning; the epic's check with `TARGET=split-long-reqs-verdict-narrative` and `CAPS=night-card` prints `OK: night-card` with 4 scenarios added; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #248 |

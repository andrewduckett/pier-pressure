## Story

## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which requirements does this story split? | The 4 the issue names in `ha-addon`: "The form sets each pier's horizon" (11 scenarios), "The form sets each pier's equipment" (11), "The form sets each pier's GO threshold and wind-gust limit" (6) and "The form sets the broker" (7). The other 4 long `ha-addon` requirements belong to #239 and stay as they are. | Evidence: #238 and #239 bodies; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `ha-addon`? | No. Open pull requests #246 and #255 do not edit `openspec/specs/ha-addon/`. The stack's other pull requests edit other specs, and #258, the layer below, is this branch's base. | Evidence: `gh pr list`; `gh pr diff <n> --name-only` |
| D3 | How does "The form sets each pier's horizon" split? | Into six, one per behavior: `min_altitude` sets a flat floor; `horizon_points` become the horizon points, and blank text is unset; no horizon field takes the horizon from `config.yaml`, else flat at 0; unreadable points skip the pier; points that fail the inline checks, or both fields set, skip the pier; a `horizon` value beside a set field skips the pier. Its stop rule goes to D7. | Assumption (the user delegated the brainstorm). Evidence: `openspec/specs/ha-addon/spec.md` |
| D4 | How does "The form sets each pier's equipment" split? | Into six: set fields build the equipment; the reducer defaults to 1.0; no equipment field takes the equipment from `config.yaml`, else none; incomplete equipment skips the pier; a value of 0 or less skips the pier; an `equipment` value beside a field skips the pier. Its stop rule goes to D7. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D5 | How does "The form sets each pier's GO threshold and wind-gust limit" split? | Into four: set values pass to the pier; an unset value comes from `config.yaml`, with what counts as unset; with neither source, the file defaults apply; a bad value skips the pier. Its stop rule goes to D7. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D6 | How does "The form sets the broker" split? | Into six: a host on the form sets all four connection settings; a blank broker field is unset; login fields without a host stop the add-on; a rejected form login points to the form's login; the log names the Configuration tab; no log line or error reveals the password. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D7 | Where does "When every pier is skipped, the add-on SHALL stop" go? | The horizon, equipment and gate requirements each state it. It becomes one requirement that, like the originals, names no cause, with the two scenarios that test it. So 3 identical SHALL become 1. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D8 | What happens to the three pointers to "The add-on combines the Configuration form with config.yaml"? | #237 removed that heading, so the horizon, equipment and gate requirements point at nothing. Their new requirements name "A pier in config.yaml adds its settings to the form pier with its id" instead. A pointer requires nothing, so no meaning changes. | Evidence: `openspec/specs/ha-addon/spec.md`; #237's archived delta |
| D9 | Is any pointer left aimed at a heading this story removes? | One: "The add-on uses the Supervisor's MQTT broker when the settings name none", which #239 owns, points to "The form sets the broker". This change MODIFIES that requirement only to retarget its two pointers. The second pointer names the heading #237 removed, and now names "The broker connection and the recompute interval each count as one setting". Its text and scenarios stay otherwise word for word. | Assumption. Evidence: `grep` of `openspec/specs`, `docs`, `README.md`, `pierpressure`, `tests`, `card/src` |
| D10 | Which pointers to removed headings does this story leave? | Three to "The add-on combines the Configuration form with config.yaml", which #237 removed: one in "The add-on reads config from its own config folder" and two in "The core checks every saved setting". Both requirements belong to #239, which splits them. The pull request names them. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D11 | How many scenarios does this story add? | None. Every new requirement gets at least one of the 35 existing scenarios, so strict validation needs no new one. | Evidence: the draft delta in `.workspace/` |
| D12 | Does the code disagree with any of the four requirements? | No drift found. Checked against `pierpressure/addon_options.py`, `pierpressure/__main__.py`, `pierpressure/supervisor.py` and `pierpressure/core/config.py`. | Evidence: those files |
| D13 | May the SHALL text be reworded? | Only so that each new requirement reads on its own: naming its subject again ("inside an add-on", "a pier on the Configuration form"), and repeating "SHALL be skipped" and "SHALL still be published" in each skip requirement. Two lead sentences whose bullets carry every case ("SHALL turn … into that pier's horizon", and its equipment twin) and one ("the form's broker fields SHALL work as follows") are dropped. Every other SHALL and SHALL NOT keeps its meaning. | Evidence: #230 Shared decision 3 |
| D14 | Which words do the new headings use? | The spec's own words (Configuration form, pier, horizon, equipment, `go_threshold`, `max_gust`, broker, connection settings). `openspec/glossary.md` defines no add-on term, and no term is new. No ADDED heading repeats a heading the delta removes or one the spec keeps. | Evidence: `openspec/glossary.md`; #230 Shared decision 5 |
| D15 | What does "done" mean for this story? | `openspec validate split-long-reqs-ha-addon-form-fields --strict` passes before archive; after archive none of the four leaves a long-requirement warning, and `ha-addon` keeps the 4 that #239 owns; the epic's check with `TARGET=split-long-reqs-ha-addon-form` and `CAPS=ha-addon` prints `OK: ha-addon` with no scenario added; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #258 |

## 1. The panned axis, as pure functions

- [x] 1.1 [medium] `stripReach(states, pier, opening)` in `card/src/strip.ts` returns the reach: from the start of the earliest timeline hour to the end of the latest, across every `ROWS` sensor and the two Cloud range sensors, widened to cover `opening`. A point with a readable `datetime` counts its own hour, whatever its value; a Rain chance point counts only when it holds a number, and then for the hour before its time; an `unavailable` sensor and an unreadable `datetime` count nothing. Cases: Cloud cover hourly from 2026-10-31T12:00:00Z to 2026-11-03T11:00:00Z gives 12:00Z to 2026-11-03T12:00:00Z; a Rain chance `20` at 12:00Z as the earliest point starts it at 11:00Z; a null Rain chance at 12:00Z beside other sensors from 12:00Z starts it at 12:00Z; a last Cloud cover point with `null` at 2026-11-02T11:00:00Z ends it at 12:00Z; an unavailable Seeing to 2026-11-03 is left out; points inside the opening axis give the opening axis (design D-3; test: new `card/test/pan.test.ts`) (verify: mise exec -- npm --prefix card test -- pan) (✓ npm test -- pan passed, 10 tests; full card suite 405 passed; typecheck passed)
- [x] 1.2 [medium] `buildStrip` takes an optional `start`. Without it the axis is the opening axis, as today; with it, the axis starts at `start` clamped into the reach and is as long as the opening axis. The `Strip` carries `opening` and `reach`. ## 2. Panning the card [depends-on: 1]

- [x] 2.1 [medium] With the strip focused, Right pans the axis an hour later and Left an hour earlier, inside the reach. The strip has `tabindex="0"`, `role="group"` and the accessible name "Night strip. Use the Left and Right arrow keys to move through the forecast." The card holds `heldStart`: a pan whose clamped start equals the start on screen changes nothing; one that lands on the opening axis's start clears it; new state and the minute redraw keep a held start; a reach that moves past it moves the axis only as far as needed; a new pier in `setConfig` clears it. Scenarios: "One hour later", "At the end of the reach", "New state after a pan", "A minute passes after a pan", "The forecast moves on past the axis", "A new night of another length", "Panning back by hand", "A new pier", "A pan against the reach's start" (design D-2, D-7; test: `card/test/pan.test.ts`) (verify: mise exec -- npm --prefix card test -- pan) (✓ npm test -- pan passed; full card suite 428 passed; typecheck passed; removing the pier reset or the pan-back rule fails its test)
- [x] 2.2 [easy] A "Back to tonight" button sits on its own line above the strip, outside it. It is `hidden` while the axis is the opening axis, and the card's styles keep a hidden button's place with `visibility: hidden`; it is at least 24 px tall. Clicking it returns the axis to the opening axis and focuses the strip. A pointer press with a 12 px move on the button, then a `click`, leaves the axis on the opening axis (design D-8; test: `card/test/pan.test.ts`) (verify: mise exec -- npm --prefix card test -- pan) (✓ npm test -- pan passed; full card suite 437 passed; typecheck passed)
- [x] 2.3 [complex] A pointer drag pans the axis by the sideways distance's share of the time-label track's width, recorded at `pointerdown`: left by a quarter of the width on a 24-hour axis moves it 6 hours later, right moves it earlier. Only the primary pointer's main button starts a drag, and no drag starts while one is active. It starts to pan only once the pointer has moved more than 8 px sideways and further sideways than up or down, and then captures the pointer. `pointercancel` puts the axis back where the gesture began; `pointerup` and `lostpointercapture` end it where it is. A track width of 0 pans nothing. The strip's styles carry `touch-action: pan-y` and `user-select: none`. Scenarios: "A drag to the left", "A touch swipe to the right", "A tap that slips", "Scrolling past the card on a phone", "A mostly vertical drag", "A second finger" (design D-5; test: `card/test/pan.test.ts`, with `getBoundingClientRect` stubbed) (verify: mise exec -- npm --prefix card test -- pan) (✓ npm test -- pan passed; full card suite 453 passed; typecheck passed)
- [x] 2.4 [easy] A wheel event over the strip with `|deltaX| > |deltaY|` pans by `deltaX`'s share of the track's width and calls `preventDefault`, even at the reach's end; a mostly vertical one changes nothing and is not prevented. `deltaMode` 1 counts 16 px a line, and 2 the track's width a page. Scenarios: "A trackpad swipe", "A mouse wheel scrolls the page" (design D-6; test: `card/test/pan.test.ts`) (verify: mise exec -- npm --prefix card test -- pan) (✓ npm test -- pan passed; full card suite 459 passed; typecheck passed; a passive listener fails two tests)

- 2026-11-07: task 2.2's button line sits between the darkness note and the strip. `card/test/messages.test.ts` checked that the strip was the note's next sibling, which is stricter than the spec's "between the confidence and the strip". The test now checks the order: summary, note, strip.
- 2026-11-07: task 4.1's touch check in a real browser found that a swipe stopped after its first move. A touch pointer starts captured by the cell under the finger. When the strip captures it, the cell's `lostpointercapture` bubbled up to the strip and ended the drag. The strip now ends a drag only on its own `lostpointercapture`, with a test in `card/test/pan.test.ts`. A mouse has no such capture, so task 2.3's mouse tests could not show it.
- 2026-11-07: the code review found that a mouse or pen drag could be lost at the strip's edge, because design D-5 captured the pointer only once the drag started to pan. The strip now captures the pointer at `pointerdown`. D-5 deferred capture so that a press on the Back to tonight button would not lose its click; D-8 moved the button outside the strip, so that reason no longer holds.

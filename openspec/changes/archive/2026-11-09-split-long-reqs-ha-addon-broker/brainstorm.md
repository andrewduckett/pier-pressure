## Decisions

| # | Question | Answer | Source |
|---|---|---|---|
| D1 | Which requirements does this story split? | The last 4 long `ha-addon` requirements, as the issue names them: "The add-on uses the Supervisor's MQTT broker when the settings name none" (8 scenarios), "The core checks every saved setting" (2), "The add-on waits a bounded time for the Supervisor's broker" (4) and "The add-on reads config from its own config folder" (3). No other `ha-addon` requirement is long. | Evidence: #239 body; `openspec validate --specs --json` |
| D2 | Does a change already in flight touch `ha-addon`? | No. Open pull requests #246, #255 and the stack's other layers do not edit `openspec/specs/ha-addon/`. #258 and #259 do, and #259 is this branch's base. | Evidence: `gh pr list`; `gh pr diff <n> --name-only` |
| D3 | How does "The add-on reads config from its own config folder" split? | Into three: the service reads `config.yaml` from the add-on's config folder; that file uses the same keys as outside Home Assistant and holds only what the form leaves unset; with no file, the add-on starts with the form's settings. | Assumption (the user delegated the brainstorm). Evidence: `openspec/specs/ha-addon/spec.md` |
| D4 | How does "The add-on uses the Supervisor's MQTT broker when the settings name none" split? | Into seven: the add-on wants the `mqtt` service but does not need it; a host in `config.yaml` sets all four connection settings, from one source; with no host set, all four come from the Supervisor; topic settings come from `config.yaml` or their defaults; a port or login in the file without a host is rejected; outside an add-on the Supervisor is never asked; requests to the Supervisor bypass any proxy. The broker-source log scenario sits under the Supervisor requirement. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D5 | How does "The add-on waits a bounded time for the Supervisor's broker" split? | Into four: the service keeps asking while the broker is "not provided yet", with the four cases; the wait starts no request after 60 seconds, each request times out within 5 seconds, and usable details end it; no broker within 60 seconds stops the add-on; a refused service stops it at once. "Neither error SHALL say that `config.yaml` is not read" is stated in each of the two error requirements. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D6 | How does "The core checks every saved setting" split? | Into four: the core checks each saved setting as it checks `config.yaml`, and the add-on passes on what it does not expect; the add-on only reads, renames and combines, and ignores top-level keys the form does not declare; an unset form field is left out before the core checks the pier; saved values of the wrong shape stop the add-on. | Assumption. Evidence: `openspec/specs/ha-addon/spec.md` |
| D7 | How many scenarios does this story add? | Two, both under D6's split, which has only 2 scenarios for 4 requirements: "The add-on renames form fields for the core" and "A field saved as null is left out". Each restates a SHALL its requirement keeps. Existing tests assert them: `test_a_form_with_piers_becomes_the_config_files_shape`, `test_a_horizon_floor_becomes_a_horizon_block` and `test_every_optional_pier_field_saved_as_null_is_left_out`. The pull request lists them. | Assumption. Evidence: `tests/test_addon_options.py`; #230 Shared decision 4 |
| D8 | Where do the three pointers to the heading #237 removed go? | "The add-on combines the Configuration form with config.yaml" no longer exists. In the config-folder split it becomes "The add-on builds one set of settings from the form and config.yaml". In the setting-check split, the pointer on unset fields becomes "An empty or blank form field counts as not set", and the pointer on combining rules becomes "The add-on builds one set of settings from the form and config.yaml". A pointer requires nothing, so no meaning changes. | Evidence: `openspec/specs/ha-addon/spec.md`; PR #259 "Pointers" |
| D9 | Is any pointer left aimed at a heading this story removes? | Two spec pointers named "The add-on uses the Supervisor's MQTT broker when the settings name none". The one in the config-folder requirement is rewritten in its split. The other is in "A broker host on the form sets all four connection settings", which this change MODIFIES only to name the two requirements that now decide the source. Its scenarios stay word for word. After archive, no spec pointer names a missing heading. | Evidence: a pointer check of every quoted heading in `openspec/specs` |
| D10 | What about code comments that name a removed heading? | Left as they are, because the epic changes no code or test. `pierpressure/supervisor.py` cites "The add-on waits a bounded time for the Supervisor's broker", and `tests/test_addon_settings.py` cites the heading #237 removed. The pull request names both. | Assumption. Evidence: #230 "Won't"; `grep` of `pierpressure` and `tests` |
| D11 | Does the code disagree with any of the four requirements? | No drift found. The 60-second wait, 5-second timeout, refused-access stop, proxy bypass, `mqtt:want`, shape errors and top-level handling match `pierpressure/supervisor.py`, `pierpressure/addon_options.py` and `ha-addon/config.yaml`. The code also retries cases the list does not name, such as a response that is not JSON; the list never says it is complete, so that is not drift. | Evidence: those files |
| D12 | May the SHALL text be reworded? | Only so that each new requirement reads on its own: naming its subject again ("Inside an add-on"), stating "SHALL NOT say that `config.yaml` is not read" in each of the two error requirements, and writing "before the add-on could use the Supervisor's broker" for "before this change" in the outside-an-add-on requirement. Every SHALL, SHALL NOT and MAY keeps its meaning. | Evidence: #230 Shared decision 3 |
| D13 | Which words do the new headings use? | The spec's own words (Configuration form, `config.yaml`, Supervisor, `mqtt` service, connection settings, pier, core). `openspec/glossary.md` defines no add-on term, and no term is new. No ADDED heading repeats a heading the delta removes or one the spec keeps. | Evidence: `openspec/glossary.md`; #230 Shared decision 5 |
| D14 | What does "done" mean for this story? | `openspec validate split-long-reqs-ha-addon-broker --strict` passes before archive; after archive `ha-addon` has no long-requirement warning; the epic's check with `TARGET=split-long-reqs-ha-addon-form-fields` and `CAPS=ha-addon` prints `OK: ha-addon` with the 2 added scenarios; `mise run check` is green. | Evidence: #230 Shared decisions 6 and 7; the stacked base, PR #259 |

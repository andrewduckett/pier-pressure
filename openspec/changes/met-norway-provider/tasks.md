## 1. MET Norway provider

Brainstorm decisions are `D1`–`D19` in `brainstorm.md`. Put the parser and fetcher in a new `pierpressure/conditions/met_norway.py`, shaped like `nws.py`, and their tests in `tests/test_conditions_provider.py` beside the NWS tests.

- [ ] 1.1 [easy] The catalog offers `met_norway` (`MET Norway`, no key) declaring the eleven variables in D2 with the cloud bundle; `providers: [met_norway]` passes the cloud rule; the default order leaves it out (verify: `uv run pytest tests/test_provider_catalog.py tests/test_config.py -k met_norway`)
- [ ] 1.2 [medium] Parsing a `complete` payload fills each step's hour from the instant fields in D3, leaves a missing field absent with no error, and takes the issue time from `properties.meta.updated_at` in UTC, or null when it is missing (D9) (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.3 [medium] Parsing checks each variable against `meta.units` (D5): expected units are carried as reported, `m/s` wind speed and gust are multiplied by 3.6 unrounded, and any other unit leaves that variable absent in every hour (D6) (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.4 [medium] Parsing keeps only the leading run of steps one hour apart, then only hours within 72 hours of the first step (D7) (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.5 [easy] A step's `next_1_hours.details.probability_of_precipitation` is held on the hour after the step, and dropped when that hour is not a kept step (D8) (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.6 [medium] A fetch requests `https://api.met.no/weatherapi/locationforecast/2.0/complete` with only `lat` and `lon` rounded to 4 decimals and the NWS `User-Agent` (D10, D11); an error status fails the fetch; a 203 succeeds and logs a deprecation warning (D14). Use `httpx.MockTransport`, as the NWS tests do (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.7 [complex] The fetcher remembers, per rounded coordinates, its last good forecast with that response's `Expires` and `Last-Modified` (D12): before `Expires` (by its injected `now`) it makes no request; after it, it sends `If-Modified-Since`; a 304 returns the remembered forecast and takes the new `Expires`; a missing `Expires` lets the next fetch request; a missing `Last-Modified` sends no `If-Modified-Since`; a failed request forgets the remembered response (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.8 [easy] `build_provider` builds `met_norway` with its `now`, and the fill works through the stack: listed first it fills the cloud bundle; with no gust or rain chance its outcome succeeds and the next provider fills them; a 429 fails it and `open_meteo` fills cloud (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.9 [easy] A trimmed live Oslo recording, `tests/fixtures/met_norway.json` (D15; record it with the NWS `User-Agent` from `.../complete?lat=59.9139&lon=10.7522` and keep its first 4 steps), parses with every declared variable in each hour and a rain chance in each hour after the first (verify: `uv run pytest tests/test_conditions_provider.py -k met_norway`)
- [ ] 1.10 [easy] The README documents `met_norway` as D17 says: an "Adding MET Norway" section like NWS's (Nordic-only gust and rain chance, wind converted from m/s, the hourly part only, the `Expires` caching, the User-Agent), the provider key list, the health-sensor key and topic lists, the clean-up key list, and the `metar_station` line naming it among the providers with low and mid cloud (verify: `uv run pytest tests/test_docs.py -k met_norway`)
- [ ] 1.11 [easy] `docs/night-timeline.md`'s rain-chance row says MET Norway gives it only near the Nordic countries and does not publish its threshold (D17) (verify: `uv run pytest tests/test_timeline_docs.py -k met_norway`)
- [ ] 1.12 [easy] The whole project gate passes with MET Norway in place (verify: `mise run check`)
